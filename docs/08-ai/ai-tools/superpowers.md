# Superpowers：从工程工作流到 Skill 源码

> 本文合并整理两篇关于 Superpowers 的文章：一篇侧重使用方法和工程工作流，另一篇侧重 Skill 设计与提示词源码分析。

[Superpowers](https://github.com/obra/superpowers) 是一套面向 AI Coding Agent 的软件开发工作流与 Skill 集合。它不试图让 Agent “更会写代码”这么简单，而是把需求澄清、设计、计划、实现、测试、审查和收尾变成一组可触发、可组合、可验证的技能。

## 一、它解决什么问题

AI Coding Agent 通常能够快速生成代码，但工程任务的难点往往不在“写出几行代码”，而在于：

- 需求是否被正确理解
- 设计是否经过确认
- 修改是否在隔离分支中进行
- 计划是否足够具体
- 测试是否先于实现建立
- 失败时是否调查了根因
- 完成时是否提供了真实验证证据

Superpowers 的核心做法，是把传统软件工程流程编译成 Agent 可以执行的 Skill，并用规则约束 Agent 的行动顺序。

![](asset/01-superpowers-workflow.jpg)

传统的瀑布式流程可以概括为：

> 需求调研 → 设计方案 → 代码编写 → Debug → 测试 → 代码评审 → 生产部署

Superpowers 将这条流程拆成多个独立但相互衔接的 Skill，使 Agent 不再只响应一句“帮我改代码”，而是先建立上下文、边界、计划和证据链。

## 二、三层架构

Superpowers 可以从三个层次理解：

1. **引导层**：决定什么时候检查和调用 Skill。
2. **技能层**：将软件工程方法论写成可加载的 Markdown Skill。
3. **工具层**：提供工作树、子代理、测试、审查和记忆等执行机制。

### 2.1 引导层：using-superpowers

`using-superpowers` 是总开关。它要求 Agent 在开始任务前检查可用 Skill；只要某个 Skill 有哪怕很小的适用可能，就必须先调用它。

它还规定了优先级：

1. 用户明确指令
2. Superpowers Skill
3. Agent 默认行为

这意味着 Skill 不是建议清单，而是工作流控制层。用户要求与 Skill 冲突时，用户指令优先；没有冲突时，Skill 负责限制 Agent 的随意发挥。

### 2.2 技能层：可组合的工程 Skill

Superpowers 不是一个巨大的 Prompt，而是一组有明确职责的 Skill。常见 Skill 包括：

- `brainstorming`：在创造性工作前澄清目标、约束、方案和验收标准
- `using-git-worktrees`：为开发任务创建隔离工作树
- `writing-plans`：把设计拆成带文件路径、实现步骤和验证命令的计划
- `subagent-driven-development`：把任务交给独立子代理执行并审查
- `executing-plans`：按计划逐步执行并在检查点停下
- `test-driven-development`：强制执行 Red → Green → Refactor
- `systematic-debugging`：先调查根因，再提出修复
- `requesting-code-review`：根据计划和变更进行审查
- `receiving-code-review`：验证审查意见后再决定是否修改
- `verification-before-completion`：在声称完成前提供实际验证证据
- `finishing-a-development-branch`：测试、汇总并决定合并、提 PR、保留或清理分支
- `writing-skills`：用测试驱动方法创建新的 Skill

### 2.3 工具层：隔离、并行与记忆

工具层主要解决 Agent 执行时的工程风险：

- Git worktree 隔离当前分支和新任务
- 子代理隔离上下文，避免主会话被细节淹没
- ledger 或任务记录保存关键状态
- 测试和审查作为流程门禁
- 分支收尾流程避免“代码写完但工作区状态不清楚”

## 三、一个需求如何经过 Superpowers

### Step 1：brainstorming

在写代码前先确认：

- 目标是什么
- 不做什么
- 成功标准是什么
- 有哪些约束
- 现有项目结构如何组织
- 可选方案有哪些，各自的成本和风险是什么

它要求一次只问一个问题，并在设计完成后逐节确认。对于大型需求，还要先拆成多个可以独立交付的子项目。

### Step 2：using-git-worktrees

设计确认后，在隔离工作树中开始实现。标准流程包括：

1. 检查仓库状态。
2. 选择并验证工作树目录。
3. 创建分支和工作树。
4. 安装依赖并运行测试基线。
5. 确认工作区干净后再开始修改。

这样可以避免未完成的工作污染主分支，也让多个任务拥有清晰的文件边界。

### Step 3：writing-plans

计划不是一句“实现登录功能”，而应该说明：

- 修改哪些文件
- 每个文件负责什么
- 每个任务的具体步骤
- 需要增加或修改哪些测试
- 如何运行验证
- 任务之间的依赖关系

计划应遵循 DRY、YAGNI 和 TDD 原则，并拆成足够小的任务。一个不了解项目背景但具备工程能力的开发者，也应该能够按照计划执行。

### Step 4：subagent-driven-development

每个任务可以交给一个新的子代理执行。常见的两阶段审查是：

1. 规范符合性：是否按计划实现，是否遗漏要求。
2. 代码质量：设计、可维护性、错误处理和测试是否合理。

子代理完成后，主代理只接收结果和证据，减少主上下文污染。

### Step 5：test-driven-development

TDD 的硬规则是：

1. 先写一个会失败的测试。
2. 运行并确认它确实失败。
3. 写最少实现让测试通过。
4. 再重构实现。
5. 重复循环。

如果实现代码已经写完才补测试，就失去了测试作为设计约束的价值。Superpowers 甚至要求删除测试之前提前写出的实现代码，再从失败测试开始。

![](asset/09-tdd-cycle.jpg)

### Step 6：requesting-code-review

代码审查应根据计划和验收标准进行，而不是只看代码格式。审查重点包括：

- 是否满足需求
- 是否改变无关行为
- 是否处理边界和异常
- 是否引入安全或并发风险
- 测试是否覆盖真实风险
- 是否有更小、更清晰的实现

### Step 7：finishing-a-development-branch

收尾时先运行验证，再让用户选择：

- 合并到目标分支
- 创建 Pull Request
- 保留当前分支
- 丢弃本次改动

只有明确完成验证，才可以声称任务完成。

## 四、从源码角度理解 Skill

Superpowers 所谓的“源码”，主要不是传统编译型源代码，而是写在 Markdown 文件中的自然语言规则。每个 Skill 通常包含：

- 名称和触发条件
- 使用时机
- 强制规则
- 执行步骤
- 与其他 Skill 的调用关系
- 输出物和验证要求

因此，Skill 更像一种面向 Agent 的流程程序：Markdown 是源代码，模型是解释器，工具调用是执行动作，测试和审查是运行时断言。

![](asset/05-waterfall-to-agent-workflow.jpg)

### 4.1 Skill 的加载机制

在支持 Skill 的 Agent 中，通常会先加载 Skill 元数据，再按需要展开完整内容。这样可以避免每次会话都把所有规则放进上下文，同时保留按需加载能力。

`using-superpowers` 的关键作用，就是让 Agent 在回复前检查 Skill。它把“是否应该使用某个流程”从模型的临时判断，提升为显式的运行时规则。

![](asset/06-using-superpowers-skill.jpg)

### 4.2 brainstorming 的设计原则

`brainstorming` 把需求澄清本身做成一个流程程序：

- 先阅读项目状态
- 识别范围是否过大
- 一次提出一个问题
- 提供两到三个方案和优缺点
- 明确推荐方案和理由
- 设计完成后请求确认
- 只讨论与当前目标有关的重构

它避免 Agent 在需求不清时直接生成代码，把“想法”转化为“可执行规范”。

![](asset/07-brainstorming-skill.jpg)

### 4.3 writing-plans 的设计原则

`writing-plans` 要求计划包含文件级别的上下文和验证路径，并把大任务拆解成短任务。它本质上是把项目知识转换成 Agent 可执行的操作序列。

一个好的计划应同时回答：

- 改哪里
- 为什么改
- 怎么改
- 改完如何证明是对的

### 4.4 子代理和并行边界

Superpowers 同时支持子代理驱动开发和调试场景下的并行代理，但二者不能混为一谈：

- 子代理驱动开发强调任务隔离、上下文隔离和逐任务审查。
- 并行代理适合相互独立的调查、测试或调试分支。
- 有共享状态或存在顺序依赖的任务，不应强行并行。

![](asset/08-subagent-development.jpg)

并行不是默认优化。若多个 Agent 同时修改同一组文件，冲突成本可能超过节省的时间。

## 五、核心 Skill 的工程纪律

### 5.1 系统化调试

`systematic-debugging` 要求按以下顺序处理问题：

1. 收集错误信息和复现步骤。
2. 定位触发条件。
3. 追踪数据和控制流。
4. 提出根因假设。
5. 用实验验证假设。
6. 修复根因，而不是只压制错误表现。
7. 增加回归测试。

禁止在没有证据时连续尝试多个猜测性修复。

### 5.2 verification-before-completion

完成检查要求 Agent 区分“我修改了代码”和“修改已经被验证”。完成报告应包括：

- 实际运行的命令
- 测试或检查结果
- 未执行的检查
- 已知限制和剩余风险

不能用“应该可以”“看起来没问题”替代验证证据。

### 5.3 receiving-code-review

收到代码审查意见后，不应机械接受或拒绝。正确流程是：

- 判断意见是否适用于当前代码
- 用测试、文档或调用方验证事实
- 对不清楚的前提提问
- 优先修复高风险问题
- 修复后重新运行验证

## 六、writing-skills：用 TDD 创建 Skill

`writing-skills` 把 TDD 应用于 Skill 本身。一个 Skill 不是写得越长越好，而是要证明它能改变 Agent 的行为。

推荐流程：

1. 设计一个最容易失败的真实场景。
2. 先让没有该 Skill 的 Agent 执行，记录错误行为。
3. 编写最小规则，明确触发条件和禁止行为。
4. 再次运行场景，确认行为发生改变。
5. 加入边界、例外和反例测试。
6. 删除无法证明价值的冗余说明。

![](asset/11-skill-writing-tdd.jpg)

Skill 的质量可以从三个方面判断：

- **触发正确**：适用时会调用，不适用时不会误触发。
- **执行稳定**：不同上下文中仍能遵守关键规则。
- **结果可验证**：能够通过测试、命令或输出结构检查。

## 七、Superpowers 的优势与局限

### 优势

- 把隐性的工程经验显式化
- 强制需求、计划、测试和审查进入流程
- 用 worktree 和子代理降低上下文与分支污染
- 用 Evidence over claims 限制虚假完成报告
- 通过 Markdown Skill 降低流程定制门槛

### 局限

- 流程纪律会增加短任务的交互成本
- 强制串行的工作流可能成为多需求场景的吞吐瓶颈
- Skill 规则依赖 Agent 是否真的遵守，不能替代权限控制和 CI 门禁
- 子代理并不天然保证结果正确，仍需测试和审查
- 一套面向单需求执行的工作流，不等于完整的项目调度系统
- 过度使用生命周期流程，可能让低风险小改动变得笨重

因此，Superpowers 更适合作为“执行引擎”：帮助 Agent 有纪律地完成一个工程任务。若要支持多需求调度，还需要额外的队列、依赖图、优先级、资源配额、状态持久化和跨任务协调层。

## 八、适用边界与实践建议

适合使用 Superpowers 的场景：

- 跨多个文件的功能开发
- 需要测试、审查和回归的工程任务
- 高风险重构或数据库变更
- 需要多个 Agent 协作的复杂任务
- 团队希望统一 AI Coding 流程

不必强行使用完整流程的场景：

- 只读问答
- 简单的拼写或格式修正
- 已有明确测试且影响范围很小的局部修改
- 不涉及代码变更的资料查询

实践时可以按风险分层：低风险任务只使用验证和审查；中风险任务增加计划和测试；高风险任务完整使用 brainstorming、worktree、TDD、审查和分支收尾。

## 结语

Superpowers 的价值不在于增加了多少 Prompt，而在于把“一个可靠的软件工程师会遵守的工作纪律”变成 Agent 可以加载和执行的 Skill。

它把 Agent 从“会生成代码”推向“会按工程流程完成任务”，但最终质量仍取决于：需求是否清楚、边界是否明确、测试是否真实、权限是否受控，以及完成声明是否有证据支撑。
