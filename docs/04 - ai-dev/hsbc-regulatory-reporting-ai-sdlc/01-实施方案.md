# 01 实施方案

## 1. 目标与范围

目标是把监管报送项目从“需求进入 Jira、文档散落、审批难追溯”改造成一个由工件驱动的循环：每一阶段提交一个可审计工件，下一阶段读取该工件，人工只在需要判断的门上审批。

首版覆盖监管报表需求、字段映射、数据处理、规则变更、测试、发布和运行反馈。方案不假设某个具体市场或报表已经获得法律确认；实际试点必须选择一个市场、一个官方报表编号和一条数据链路。

## 2. 总体流程

```mermaid
flowchart LR
    A[监管来源或生产事件] --> B[intent.md]
    B --> C[Jira Requirement / Epic]
    C --> D[spec.md]
    D --> E[Jira Story / Capability]
    E --> F[plan.md]
    F --> G[Jira Task / Sub-task]
    G --> H[实现与测试证据]
    H --> I[PR Review]
    I --> J[发布审批]
    J --> K[运行监控与报送]
    K --> A
```

## 3. 阶段与责任

| 阶段 | 主要工件 | Jira 状态 | 主要责任人 | 必须人工决定 |
| --- | --- | --- | --- | --- |
| Plan | `intent.md` | Draft → Analysis | 业务发起人、产品负责人 | 是否值得分析 |
| Design | `spec.md` | Compliance Review → Approved | BA、架构师、合规负责人 | 监管解释、范围和风险是否可接受 |
| Build | `plan.md`、代码、测试 | In Progress → Testing | 工程师、AI 代理 | 技术方案和高风险变更 |
| Test | 测试报告、数据质量证据 | Testing → Review | QA、数据负责人 | 是否满足验收和控制目标 |
| Deploy | PR、发布记录 | Review → Release Approval → Done | 技术负责人、发布经理 | 是否允许进入生产 |
| Maintain | 事件诊断、复盘、回滚记录 | Done → Triage | 服务负责人、值班人员 | 是否创建新需求或执行回滚 |

## 4. 风险分级

| 等级 | 示例 | AI 权限 | 人工门 |
| --- | --- | --- | --- |
| R1 | 文档格式、非敏感说明文字 | 可生成 PR | 文档负责人抽查 |
| R2 | 非核心报表字段、测试数据规则 | 可修改分支和运行测试 | Story Owner + QA |
| R3 | 监管规则、核心字段映射、报送计算逻辑 | 只能提出变更并生成证据 | 合规负责人 + 架构师 + QA |
| R4 | 数据驻留、跨境、生产发布、回滚 | 只读诊断或准备 PR | 数据保护、安全、发布经理联合审批 |

任何无法确定风险等级的变更按更高等级处理。

## 5. 数据边界

AI 会话、Jira 和 Git 默认只接受：监管元数据、字段定义、脱敏样例、统计结果、规则版本和受控证据链接。客户身份、交易明细、原始监管文件和 Token Vault 内容不得直接进入这些系统。需要分析原始数据时，代理只能调用属地系统提供的受控、最小化、审计记录完整的接口。

## 6. 落地原则

1. Jira Key 是所有工件的关联主键。
2. 每个工件必须包含版本、作者、审批人、来源和验证状态。
3. 计划、实现和测试不一致时，先更新 `plan.md`，再继续实现。
4. Skill 的建议不能替代合规审批；确定性规则必须在 CI、Hook 或 PR 检查中重跑。
5. 生产门之外的操作可以自动化，生产发布必须保留人工授权。
