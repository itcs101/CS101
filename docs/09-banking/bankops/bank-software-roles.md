---
title: 银行软件系统的内外部角色与开发任务
---

本文讨论银行在建设和维护不同类型软件时，需要参与的内部和外部角色，以及这些角色在软件开发生命周期中的具体任务。重点覆盖四类系统：

- 面向客户交易的软件；
- 重要核心账务软件；
- 计量、核算和财务风险软件；
- 监管报送软件。

这些系统可以共享研发平台和工程方法，但不能共享完全相同的审批标准。越接近客户资产、总账、资本计量和监管报送，越需要强化业务责任、独立验证、审计证据、变更控制和生产支持。

本文采用一个基本责任原则：**谁拥有业务结果，谁就是业务 Owner；谁拥有风险判断，谁负责独立挑战；谁拥有系统实现，谁负责技术交付；谁拥有生产流程，谁负责运营控制；谁拥有监管解释，谁负责监管口径。**

## 1. 角色分类

银行软件项目的角色可以分为五组：

1. **业务与运营角色**：定义业务目标、流程、产品和日常操作。
2. **控制与治理角色**：识别风险、解释监管要求、批准控制和独立评价结果。
3. **IT 与工程角色**：负责架构、开发、测试、部署、基础设施和生产支持。
4. **数据与计量角色**：负责数据、模型、算法、核算口径和报表血缘。
5. **外部角色**：包括软件供应商、云服务商、实施伙伴、外部审计师、监管机构和清算网络。

## 2. 端到端软件开发生命周期

| 阶段 | 核心问题 | 主要产出 |
| --- | --- | --- |
| 立项与意图 | 为什么做，服务谁，影响什么 | 项目章程、业务目标、初步风险评估 |
| 需求分析 | 系统必须做什么，不能做什么 | 业务需求、监管要求、用户故事、流程模型 |
| 方案与架构 | 如何实现，如何集成和控制 | 方案设计、架构设计、数据模型、接口契约 |
| 开发与配置 | 如何把设计变成可运行的软件 | 代码、配置、规则、数据库变更 |
| 测试与验证 | 功能、数据、控制和性能是否正确 | 测试报告、缺陷记录、独立验证报告 |
| 发布与迁移 | 如何安全进入目标环境 | 发布包、迁移方案、回滚方案、审批记录 |
| 运行与支持 | 生产是否稳定，问题如何处理 | 监控、事件、问题、服务请求和运行报告 |
| 变更与退出 | 如何持续改进或安全下线 | 变更记录、版本记录、数据迁移和归档证明 |

## 3. 三类项目发起模式

银行软件项目不一定都由同一个部门发起。项目的发起原因不同，业务 Owner、风险重点和验收指标也不同。

### 3.1 产品驱动型项目

新金融产品通常由业务部门的产品经理主导。产品经理对产品定位、客户价值、产品规则、业务收益和产品生命周期负责；业务架构师负责把产品想法整理为端到端流程、岗位职责、数据需求和系统能力。

```text
产品想法
    → 业务流程和业务能力
    → 新产品风险分析
    → Buy / Build / Upgrade / Reuse 评估
    → 产品审批
    → IT 实施和运营准备
```

产品经理的主要产出包括产品说明、业务规则、客户范围、流程方案、非金融风险分析和上线后的业务指标。产品经理可以提交风险分析，但不能替代风险职能进行独立审批。

### 3.2 监管驱动型项目

反洗钱、制裁、客户尽职调查、监管报送、资本、流动性和数据留存等项目通常由监管要求触发。此类项目的起点不是“要开发一个功能”，而是“银行必须满足一项外部义务”。

```text
监管来源
    → 合规解释和适用范围
    → 业务、数据、流程和系统影响分析
    → 控制设计和系统改造
    → 报送/筛查/监控验证
    → 监管证据和持续复审
```

合规或监管报送负责人负责监管解释；业务、财务、风险和数据负责人确认实际口径；IT 负责实现。监管要求的解释、风险接受和例外批准不能由开发团队自行决定。

### 3.3 COO 主导的运营效率项目

流程自动化、运营集中化、直通式处理、对账优化、减少人工操作和服务质量提升等项目通常由 COO 或运营管理层主导。

COO 对端到端运营效率、服务质量、运营成本和流程控制结果负责，但不替代业务产品 Owner、风险 Owner 或 IT 交付 Owner。

典型流程是：

```text
运营问题或效率目标
    → 流程诊断和基线度量
    → 自动化机会识别
    → 业务、控制和 IT 方案
    → 效率与控制验证
    → 运营推广和持续改进
```

效率项目不能只用节省人力作为成功标准，还必须验证错误率、例外率、客户影响、控制有效性和业务连续性。

## 4. 通用内部角色

### 4.1 业务发起人和业务 Owner

业务发起人提出问题、机会或监管变化，业务 Owner 对系统解决的问题、业务结果和上线后的持续运营负责。根据项目类型，业务 Owner 可以是产品负责人、监管报送负责人、金融犯罪负责人或 COO 指定的流程负责人。

主要任务：

- 说明业务目标、客户影响、产品范围和优先级；
- 确认业务流程、角色、例外和人工操作；
- 确认需求是否符合产品政策和业务策略；
- 参与需求评审、用户验收和生产放行；
- 对“系统上线后业务是否真正可用”承担责任。

业务 Owner 不能把需求责任完全转移给 IT。IT 可以帮助实现需求，但不能替业务决定产品规则、客户承诺、监管解释或风险接受。

### 4.2 产品经理

产品经理是产品驱动型项目的主要业务 Owner，负责：

- 产品定位、客户范围、渠道、定价和生命周期；
- 产品规则、客户承诺、业务收益和服务指标；
- 新产品业务说明和非金融风险分析的提交；
- 协调信用风险、操作风险、合规、AML、安全和数据保护评审；
- 确认产品上线条件、用户验收和上线后的业务效果。

信贷风险属于金融风险，应由信用风险职能独立评估；不能把信贷风险归入“非金融风险”分析项。非金融风险通常包括操作、合规、金融犯罪、技术、信息安全、数据保护、第三方、模型和业务连续性风险。

### 4.3 业务架构师和业务分析师

业务架构师负责把业务目标和产品规则转化为端到端业务流程、业务能力、组织职责和系统边界；业务分析师进一步将其细化为需求和可验收标准。

主要任务：

- 编写业务需求和用户故事；
- 建立业务术语、状态、规则和例外清单；
- 组织业务流程、用户旅程和业务场景建模；
- 维护需求与测试、数据字段、报表和控制点之间的追溯；
- 协调业务用户、运营、风险、合规和 IT 的意见；
- 参与缺陷分类和需求变更分析。

业务架构师还需要组织 Buy / Build / Upgrade / Reuse 分析，但不单独决定采购或技术方案；该决策应由业务、架构、IT、风险、财务和采购共同完成。

### 4.4 COO、运营负责人和流程负责人

COO 负责运营效率和端到端流程结果，运营负责人负责系统上线后的实际操作，流程负责人负责流程效率、控制和责任边界。COO 主导的项目必须明确一个具体流程 Owner，避免 COO 只作为行政发起人而没有人对实际流程负责。

主要任务：

- 定义开户、交易、结算、对账、核算、报送和异常处理流程；
- 设计人工复核、双人复核、授权和职责分离；
- 提供真实但经过脱敏的操作场景和历史问题；
- 参加用户验收测试、演练、迁移和彩排；
- 定义运营指标、服务时间、积压阈值和升级路径；
- 编写操作手册和业务连续性预案。

### 4.5 风险管理

风险管理负责识别系统可能引入或放大的信用、市场、流动性、操作、模型、国家和集中度风险。信用风险、市场风险和流动性风险属于金融风险；操作、合规、技术、金融犯罪和数据保护风险属于非金融风险或控制职能关注的风险领域。

主要任务：

- 参与立项和新产品风险评估；
- 定义限额、阈值、预警和升级机制；
- 评估计算逻辑、数据质量和模型结果对风险管理的影响；
- 审阅权限、人工干预、异常处理和应急方案；
- 验证风险报告和管理信息的完整性；
- 对重大风险例外提出接受、缓解或阻断意见。

### 4.6 合规、金融犯罪和监管关系

合规部门把法律法规、监管要求和内部政策转化为系统控制和业务流程。

AML 不是上线前附加的一张检查表，而是贯穿客户准入、KYC、交易筛查、交易监控、告警处理、可疑交易报告和客户退出的横向控制。AML 负责人必须在产品和流程设计阶段参与。

主要任务：

- 识别适用的监管机构、法规、报表和生效日期；
- 定义客户尽职调查、制裁、反洗钱、市场行为和消费者保护要求；
- 审查监管报送口径、报送频率、报送截止时间和留痕要求；
- 确认哪些判断必须由人工完成，哪些可以自动化；
- 审批合规风险、政策例外和监管解释；
- 参与验收、发布和监管问询响应。

监管报送也不是 IT 单独负责的文件生成工作。合规负责监管解释，报送业务专家负责报表口径，业务/财务/风险负责源数据和计算含义，数据团队负责血缘和质量，报送运营负责复核、提交、回执和补报，IT 负责抽取、转换、校验和接口。

### 4.7 财务、会计、税务和产品控制

这些角色负责金融交易如何反映为会计分录、损益、资产负债表、资本和税务数据。

主要任务：

- 定义科目、会计事件、借贷规则、计息、费用和收入确认；
- 确认产品估值、减值、准备金和公允价值处理；
- 审阅总账、分户账、子账和管理报表之间的核对关系；
- 参与月结、季结、年结和监管财务报告测试；
- 确认账务调整、手工分录和重算规则的授权；
- 提供财务口径与监管口径之间的差异说明。

### 4.8 数据治理、数据管理和数据质量

数据角色负责让软件使用的数据可理解、可追踪、可保护和可重现。

主要任务：

- 定义数据所有者、数据管理员和数据分类；
- 维护数据字典、主数据、参考数据和业务术语；
- 绘制源系统到交易、账务、计量和报送字段的数据血缘；
- 建立完整性、准确性、一致性、及时性和唯一性规则；
- 管理数据问题、质量阈值、豁免和整改；
- 确认留存、归档、删除、备份和跨境处理要求。

### 4.9 架构、工程和 IT 交付

IT 交付角色负责把业务和控制要求实现为稳定、可维护、可审计的系统。

主要角色包括：

- 企业架构师：确认系统与集团架构、业务能力和技术标准一致；
- 领域架构师：负责交易、账务、风险、财务或监管报送领域设计；
- 解决方案架构师：负责应用、数据、集成、安全和部署方案；
- 开发人员：实现代码、规则、接口、批处理、报表和配置；
- 技术负责人：管理技术方案、代码质量、依赖和技术风险；
- 数据库和中间件工程师：负责存储、消息、批处理和运行平台；
- DevOps/平台工程师：负责流水线、环境、发布、配置和自动化；
- SRE/生产工程师：负责可用性、容量、监控、事件和恢复。

## 5. 客户交易软件的角色与任务

客户交易软件包括网上银行、移动银行、客户门户、支付发起、客户服务和交易工作台等。

### 5.1 主要内部角色

| 角色 | 主要任务 |
| --- | --- |
| 客户业务负责人 | 定义客户场景、服务目标和业务优先级 |
| 产品经理 | 设计产品功能、客户流程、价格和服务规则 |
| 客户体验/服务设计 | 设计页面、交互、无障碍和错误提示 |
| 客户运营 | 设计开户、服务请求、投诉和人工接续流程 |
| 支付/交易运营 | 定义交易处理、限额、撤销、拒绝和异常处理 |
| 金融犯罪合规 | 定义筛查、交易监控和可疑行为处置 |
| 信息安全 | 负责身份认证、设备风险、会话安全和反欺诈 |
| IT 产品团队 | 开发前端、API、交易编排和后台服务 |
| 可用性与性能工程 | 验证高峰流量、延迟、容量和降级方案 |

### 5.2 软件开发重点

- 客户身份、认证、授权和会话管理；
- 交易确认、幂等、重复提交和防止重放；
- 实时限额、余额展示和交易状态一致性；
- 交易失败、超时、冲正和客户通知；
- 客户数据最小化、隐私和日志脱敏；
- 多渠道一致性，包括柜面、客服、移动端和网上银行；
- 无障碍、可用性、语言、时区和本地化；
- 业务连续性、灾备、流量切换和客户沟通。

客户交易软件通常追求快速迭代，但涉及资金移动、客户身份和监管控制的功能仍需采用高风险变更审批。

## 6. 重要核心账务软件的角色与任务

核心账务软件包括核心银行系统、总账、分户账、产品子账、支付账务和重要会计事件处理系统。此类系统一般属于重要业务服务或关键系统，任何错误都可能影响客户资产、财务报表、资本和监管报告。

### 6.1 主要内部角色

| 角色 | 主要任务 |
| --- | --- |
| 核心账务业务负责人 | 对账户、余额、账务生命周期和业务结果负责 |
| 会计政策/财务控制 | 定义会计事件、科目、借贷和核对规则 |
| 账务运营 | 负责日结、月结、调账、冲正和异常处理 |
| 资金与流动性团队 | 关注资金头寸、流动性和现金管理影响 |
| 数据与对账团队 | 负责账务数据质量、分户账到总账的核对 |
| 领域架构师 | 设计账务模型、事件模型和系统边界 |
| 可靠性工程师 | 负责可用性、顺序处理、恢复点和恢复时间 |
| 独立验证/内控团队 | 验证账务完整性、准确性和职责分离 |

### 6.2 软件开发重点

- 账务事件必须可追踪、可重放、可冲正；
- 借贷平衡和分录完整性必须有系统性校验；
- 账户余额、可用余额、冻结金额和在途金额定义清晰；
- 交易、账务、总账和报表之间建立可重建的数据链路；
- 支持日终、月结、年结、重算、补账和批处理恢复；
- 对手工调整、特殊分录和紧急操作实行双人复核；
- 生产数据修复必须通过受控脚本、授权和完整日志完成；
- 数据迁移必须有余额核对、抽样核查、差异处理和回滚方案；
- 发布不能只验证功能，还要验证历史账务、并发、顺序和灾备恢复。

核心账务系统的测试需要包括正常路径、逆向交易、重复消息、迟到消息、部分失败、跨日处理、币种转换、时区切换和灾备恢复等场景。

## 7. 计量、核算和财务风险软件的角色与任务

这一类软件包括风险计量、资本计量、估值、减值、准备金、流动性、财务核算和管理报表系统。它们的特点是模型、数据和政策解释共同决定结果。

### 7.1 主要内部角色

| 角色 | 主要任务 |
| --- | --- |
| 计量/核算业务负责人 | 定义计算目的、口径、频率和使用者 |
| 财务与会计专家 | 定义会计政策、科目、估值和核算逻辑 |
| 风险计量专家 | 定义风险指标、资本、限额和压力场景 |
| 模型开发人员 | 开发模型、算法、参数和计算程序 |
| 模型验证团队 | 独立验证模型假设、实现、性能和稳定性 |
| 数据科学/数据工程团队 | 准备数据、特征、数据集和计算管道 |
| 产品控制/财务控制 | 分析结果、差异、调整和报表一致性 |
| 监管报告团队 | 确认结果如何进入监管报表和解释材料 |

### 7.2 软件开发重点

- 记录模型版本、参数版本、输入数据快照和运行时间；
- 区分模型代码、业务规则、参数和人工覆盖；
- 支持独立重算、结果复核和差异分析；
- 对估值、减值、资本和流动性结果保留可解释证据；
- 建立模型开发、模型验证、批准、上线和复审流程；
- 明确数据缺失、异常值、代理值和人工调整的处理方式；
- 验证大批量计算、性能、精度、舍入、币种和期间边界；
- 管理模型风险、概念变化、监管口径变化和参数更新。

模型输出不能因为“程序运行成功”就被视为正确。必须同时证明输入数据、模型实现、参数、业务解释和独立验证结果都符合批准口径。

## 8. 监管报送软件的角色与任务

监管报送软件负责将银行内部交易、客户、账务、风险和财务数据转换为监管机构要求的报表、文件或接口消息。

### 8.1 主要内部角色

| 角色 | 主要任务 |
| --- | --- |
| 监管报送负责人 | 对报送完整性、及时性和监管沟通负责 |
| 监管关系/合规负责人 | 解释监管要求、报表版本和监管反馈 |
| 报表业务专家 | 定义字段、口径、频率、校验和报送流程 |
| 数据所有者 | 对源数据、字段含义和质量负责 |
| 数据血缘/报送开发 | 实现抽取、转换、映射、校验和报送接口 |
| 财务与风险负责人 | 确认财务、资本、风险和管理口径 |
| 报送运营 | 负责报送前复核、提交、回执、补报和问询 |
| 信息安全与数据保护 | 审查敏感数据、属地、跨境和访问控制 |
| 审计/内控 | 检查报送证据、审批、完整性和可重现性 |

### 8.2 软件开发重点

- 管理监管来源、适用市场、监管机构、报表编号和版本；
- 将报表字段追溯到源系统、源字段和转换规则；
- 管理报送频率、截止时间、节假日和补报规则；
- 实现完整性、逻辑关系、跨表一致性和数值范围校验；
- 支持报送前预览、人工复核、批准、提交和回执归档；
- 保存规则版本、数据快照标识、运行批次和证据哈希；
- 对拒报、迟报、重报、修订和监管问询建立闭环；
- 按市场和数据分类控制存储、处理、日志和跨境传输；
- 允许在不复制原始敏感数据的前提下重建报送结果。

监管报送软件的“完成”不仅是生成文件，还包括证明：报表为什么这样计算、使用了什么数据、哪个版本的规则、谁复核和批准，以及监管机构是否成功接收。

## 10. 外部角色

### 10.1 软件供应商和实施伙伴

供应商可能提供核心银行、支付、交易、风险、财务或报送软件，也可能承担实施和升级工作。

主要任务：

- 提供产品能力、版本说明、接口文档和安全资料；
- 根据银行批准的需求进行配置、开发和缺陷修复；
- 提供测试包、升级影响分析、迁移工具和回滚方案；
- 说明已知问题、第三方依赖和产品生命周期；
- 配合银行进行安全测试、性能测试、审计和监管检查；
- 在生产事件中提供二线或三线支持。

银行仍然拥有业务规则、数据、风险接受、发布批准和监管责任，不能因为软件由供应商提供就把责任转移给供应商。

### 10.2 云服务商和基础设施供应商

云服务商、数据中心、网络、数据库、身份和安全产品供应商负责提供运行平台。

银行需要管理：

- 服务边界、共享责任模型和服务等级；
- 数据驻留、跨境、加密、密钥和访问权限；
- 可用区、灾备、备份、恢复和供应商退出；
- 事件通知、漏洞通告、变更窗口和审计证据；
- 供应商集中度、替代方案和业务连续性。

### 10.3 外部审计和独立评估机构

外部审计师、独立验证机构和专业咨询机构可能参与财务审计、模型验证、控制评估、渗透测试和监管整改。

主要任务：

- 按约定范围检查控制设计和运行证据；
- 独立评价模型、系统迁移、数据质量或报表流程；
- 提出缺陷、风险评级和整改建议；
- 复核整改证据，而不是替银行承担管理层审批责任。

### 10.4 监管机构和外部金融基础设施

监管机构、支付清算网络、证券托管机构、交易所和外部数据提供商不是软件项目团队成员，但会定义接口、规则、报送格式和服务约束。

项目需要管理：

- 外部规范、版本、变更通知和生效日期；
- 测试环境、认证流程、证书和接口权限；
- 报送回执、拒绝原因、补报和监管问询；
- 外部数据质量、授权范围和服务稳定性。

| 系统类型 | 首要业务责任 | 首要控制责任 | 首要 IT 责任 | 关键验收证据 |
| --- | --- | --- | --- | --- |
| 客户交易软件 | 客户体验、交易流程和服务结果 | 身份、反欺诈、合规和消费者保护 | 一致性、性能、安全和可用性 | 交易结果、异常处理、安全和性能证据 |
| 核心账务软件 | 账户、余额、账务生命周期 | 财务控制、职责分离和操作风险 | 账务完整性、顺序、恢复和迁移 | 借贷平衡、对账、重算、迁移和灾备证据 |
| 计量核算软件 | 计量口径、会计和风险结果 | 模型风险、财务控制和独立验证 | 可重现计算、版本和数据快照 | 模型验证、结果重算、差异和参数证据 |

## 12. RACI 设计建议

在正式项目中，不建议只写部门名称，应为每项关键活动指定具体角色。最少应覆盖以下活动：

| 活动 | Responsible 执行 | Accountable 最终负责 | Consulted 征询 | Informed 知会 |
| --- | --- | --- | --- | --- |
| 新产品风险分析 | 产品经理、业务架构师 | 产品业务负责人 | 信用风险、操作风险、合规、AML、安全、数据保护、IT | 产品审批委员会、审计 |
| 业务需求确认 | BA、产品团队 | 业务负责人 | 运营、风险、合规、IT | 审计、供应商 |
| COO 效率项目立项 | COO 办公室、流程团队 | COO | 流程 Owner、业务、运营风险、IT、数据 | 管理层、审计 |
| 账务规则确认 | 财务、账务运营 | 财务/产品控制负责人 | 风险、数据、架构 | 审计、监管报送 |
| 数据血缘确认 | 数据工程师、数据管理员 | 数据所有者 | 报送、财务、风险、合规 | 审计、运营 |
| AML 控制设计 | AML/金融犯罪团队、业务分析师 | 金融犯罪风险负责人 | 产品、运营、数据、IT、合规 | 审计、监管关系 |
| 架构设计 | 解决方案架构师 | 架构评审委员会或技术负责人 | 安全、数据、运营、供应商 | 业务、审计 |
| 测试验收 | QA、业务测试人员 | 业务负责人 | 合规、风险、IT | 发布经理 |
| 生产发布 | DevOps、生产工程师 | 发布经理或变更委员会 | 业务、风险、合规、安全 | 审计、供应商 |
| 监管报送放行 | 报送运营 | 监管报送负责人 | 合规、财务、数据、IT | 高级管理层、审计 |
| 重大事件处理 | 生产、运营、供应商 | 服务负责人 | 安全、风险、合规、业务 | 管理层、监管关系 |

## 13. 核心原则

1. **业务负责结果，IT 负责实现，控制职能负责挑战和监督。**
2. **核心账务、计量核算和监管报送必须能够重现结果。**
3. **软件供应商可以提供产品和服务，但不能替代银行的管理责任。**
4. **需求、数据、规则、代码、测试、审批和生产结果必须能够相互追溯。**
5. **高风险系统的发布必须同时证明功能正确、数据正确、控制有效和运行可恢复。**
6. **产品经理提交新产品风险分析，但风险职能必须保持独立评审和挑战。**
7. **AML 和监管报送是贯穿业务、数据、运营和 IT 的横向责任，不是 IT 的外围任务。**
8. **COO 对运营效率负责，但每个效率项目仍需有明确的流程 Owner、控制 Owner 和 IT 交付 Owner。**
