# 动态代码分析工具

动态代码分析是在程序运行过程中观察、记录和分析实际行为的方法。它与静态分析互补：静态分析回答“代码可能怎样运行”，动态分析回答“这次运行实际发生了什么”。

## 可以分析什么

- 函数调用路径、调用次数和耗时
- 内存分配、泄漏和对象生命周期
- CPU 热点、锁等待和线程调度
- 网络请求、数据库查询和外部依赖
- 测试覆盖到的分支和执行路径
- 运行时错误、异常上下文和用户操作
- 安全敏感数据的流动和危险 API 使用

## 常见工具类型

| 类型 | 典型工具 | 主要用途 |
| --- | --- | --- |
| 调试器和断点 | VS Code Debugger、LLDB、GDB | 查看变量、堆栈和控制流 |
| 性能分析器 | Chrome DevTools、Node.js Inspector、py-spy、JFR | CPU、内存和异步任务分析 |
| 覆盖率工具 | Istanbul/nyc、coverage.py、JaCoCo | 测量测试执行到的代码路径 |
| 追踪与观测 | OpenTelemetry、Application Insights、Jaeger | 跨服务追踪请求和依赖 |
| 运行时安全分析 | Frida、动态污点分析工具 | 观察数据流、系统调用和敏感操作 |

## 基本工作流

1. 明确要验证的假设，例如“这个接口的慢点来自数据库查询”。
2. 选择最小观测范围，避免记录整个系统的所有事件。
3. 使用代表性输入运行程序或测试。
4. 收集调用、耗时、内存、请求和错误数据。
5. 对比基线，定位瓶颈或行为差异。
6. 修改代码后重新运行同一场景，确认问题已解决。

## 动态分析与 AI 编程

AI 生成的代码可能在静态阅读上看起来合理，但运行时会暴露不同问题。可以让 AI 根据动态证据分析：

- 真实调用链是否符合设计
- 是否出现重复查询、无界重试或资源未释放
- 异常是否丢失上下文
- 并发下是否存在竞态条件
- 测试是否真正执行了目标分支

提示 AI 时应提供结构化的日志、Trace、Profile 或测试输出，而不是只说“程序很慢”或“偶尔失败”。

## 使用建议

- 先建立可重复的测试场景和性能基线。
- 只采集解决问题所需的数据，控制成本和隐私风险。
- 对生产环境使用采样、脱敏和访问控制。
- 将分析结果转化为回归测试或性能门禁。
- 不要把一次运行结果当成所有输入下的普遍结论。

## 与静态分析的关系

静态分析适合在提交前快速发现潜在缺陷、类型问题和安全模式；动态分析适合验证真实路径、性能和运行时状态。可靠的质量流程通常是静态检查先行，动态测试和观测随后，人工审查最后确认上下文。
