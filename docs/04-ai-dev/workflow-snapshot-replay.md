# Workflow Snapshot & Replay

Workflow Snapshot & Replay 是一种为自动化工作流和 AI Agent 保存状态快照，并在之后恢复、复现和审查执行过程的机制。它解决的问题是：当一个长流程中断、结果异常或需要回归时，如何从中间状态继续，而不是从头猜测。

## Snapshot 保存什么

一个有用的快照通常包括：

- Workflow 或任务的稳定 ID
- 当前步骤、状态和版本
- 输入、输出和中间结果
- Agent 使用的模型、Prompt、Skill 和工具版本
- 文件、数据库或外部系统的引用
- 已完成的副作用和待执行动作
- 错误、重试次数、限制和人工决策
- 时间戳、环境信息和权限上下文

快照不一定保存所有原始数据。敏感数据应脱敏、加密或只保存可重新验证的引用。

## Replay 做什么

Replay 是根据快照和原始输入重新执行或重放工作流。它可以有三种模式：

1. **事件回放**：只重现历史事件和界面，不重新调用外部系统。
2. **模拟回放**：使用固定的工具结果和测试数据验证 Agent 决策。
3. **真实回放**：在隔离环境中重新执行工具调用，用于回归测试和故障复现。

真实回放必须防止重复发送邮件、重复扣款、重复提交数据等副作用。

## 典型流程

```text
Start
  -> Execute step
  -> Persist snapshot
  -> Execute next step
  -> Failure or pause
  -> Restore snapshot
  -> Replay in sandbox
  -> Compare result
  -> Resume or create fix
```

## 对 AI Agent 的价值

- 让长任务可以暂停、恢复和跨 Session 继续
- 复现 Agent 的工具调用和决策上下文
- 对比不同模型、Prompt 或 Skill 的执行差异
- 为失败案例建立回归测试
- 让人工能够审查 Agent 在每一步看到了什么
- 在发布新版本前重放历史任务

## 设计重点

### 幂等性

每个有副作用的步骤都应有唯一操作 ID，并能识别重复执行。恢复流程必须知道某个动作已经完成，不能仅凭“步骤游标”再次执行。

### 一致性

快照应与代码、Prompt、Skill、工具和环境版本绑定。否则同一个快照在新版本中可能得到完全不同的结果，却无法解释差异来源。

### 可比较性

Replay 结果应比较最终状态和关键中间事件，而不是只比较模型文字。可以比较工具调用序列、参数、错误、耗时、Token 和业务结果。

### 安全性

快照可能包含凭据、用户数据和内部文件内容。应采用访问控制、加密、脱敏、保留期限和审计记录；真实 Replay 使用最小权限和隔离环境。

## 与普通日志的区别

普通日志记录“发生了什么”；Snapshot 保存“如何从这个状态继续”；Replay 则验证“在相同或受控条件下能否重新得到相同结果”。三者可以组合使用：日志用于诊断，快照用于恢复，回放用于复现和回归。

## 使用建议

- 先为关键步骤定义状态模型和快照格式。
- 在每个有副作用的边界保存快照。
- 将工具结果和外部依赖做成可替换的录制数据。
- 为失败案例自动生成 Replay 测试。
- 明确哪些步骤允许真实重放，哪些只能模拟。
- 在快照中记录版本、权限、限制和未验证假设。
